# 6. LLM Folder Specification

The `llm/` directory contains the **AI agent harness** — the ReAct loop that runs the LLM, routes tool calls, constructs system prompts, and manages multi-step reasoning. It is the brain connector between user intent and execution.

> [!IMPORTANT]
> **Folder Behavior & Philosophy:**
> 1. **Harness Only — No Business Logic**: The LLM folder orchestrates calls and dispatches tool results. It does not make trading decisions itself. All decisions emerge from the LLM's reasoning over the context built by `prompt.ts` and the tool results returned by `tools/index.ts`.
> 2. **Three Agent Roles**: The harness operates in three distinct roles — `SCREENER` (finds and deploys new positions), `MANAGER` (evaluates and closes live positions), and `GENERAL` (handles on-demand user commands). Each role receives a restricted tool subset to minimize hallucinated tool use.
> 3. **Tool Schemas are Contracts**: The tool definitions are the interface contract between the LLM and the system. Changing a tool schema (name, parameter types, descriptions) is a breaking change that also requires updating the handler and any affected prompt references in `prompt.ts`.

## Architecture Design: ReAct Agent Loop

```
  Caller (index.ts cron / telegram handler)
       │
       │  agentLoop(userMessage, role, context)
       ▼
  ┌──────────────────────────────────────────┐
  │           llm/agent.ts                   │
  │                                          │
  │  1. Build messages array                 │
  │  2. Call LLM with tool definitions       │
  │  3. LLM returns tool_call or text        │
  │     ├─ text → return to caller           │
  │     └─ tool_call ──►                     │
  │  4. executeTool(name, args) ──► result   │
  │  5. Append result to messages            │
  │  6. Loop (max config.llm.maxSteps)       │
  └──────────────────────────────────────────┘
       │
       ├── SCREENER role: deploy_position, get_top_candidates, get_active_bin, ...
       ├── MANAGER role:  close_position, claim_fees, get_my_positions, ...
       └── GENERAL role:  intent-classified subset (deploy / close / config / lessons / ...)
```

## Sub-modules

### [`llm/agent.ts`](file:///Users/ichadhr/Develop/node/meridian/agent.ts) (current root → target `llm/agent.ts`)

The core ReAct harness. Key functions:

| Function | Purpose |
| :--- | :--- |
| `agentLoop(msg, role, ctx?)` | Main entry: runs the full LLM → tool → loop until completion or max steps |
| `resolveModel(model, agentType)` | Resolves a `ModelConfig | string | null` into `{ client, model }` — handles object, string, and null formats with validation |
| `classifyError(error)` | Categorizes errors as `"retry"` (429/408/429/502/503/504/529/ECONNREFUSED/ETIMEDOUT/ENOTFOUND/ECONNRESET/EAI_AGAIN), `"failover"`, or `"fatal"` (401/403/400/413/422) |
| `buildAttemptList(model, agentType)` | Builds the full primary + fallback chain once before the step loop |
| `getToolsForRole(role, intent?)` | Returns the filtered tool definition array for a given agent role and intent |
| `classifyIntent(text)` | Regex-based intent classifier — routes GENERAL role to a minimal tool subset |

Key behaviors:
- **Multi-provider failover**: `buildAttemptList()` builds the full chain (primary + fallbacks) once per `agentLoop` call. Each step tries primary first, then walks the chain. Transient errors (429/502/503/529/ECONNREFUSED/etc.) retry up to 2× with exponential backoff. Persistent failures trigger failover to the next provider. Fatal errors (401/403/400) immediately abort.
- **Missing provider handling**: If a primary or fallback provider is not configured, `buildAttemptList()` catches the error and skips it — the next provider in the chain is tried. A missing primary does not crash the agent.
- **ModelConfig format**: Per-role model fields in `user-config.json` can be bare strings (`"openrouter/healer-alpha"`) or objects with fallback chains (`{ "provider": "openrouter", "model": "healer-alpha", "fallback": [{ "provider": "anthropic", "model": "claude-3.5-sonnet" }] }`). Legacy format is fully backward-compatible.
- **JSON repair**: LLM tool call arguments are passed through `jsonrepair` before parsing to handle malformed JSON from smaller models.
- **Step guard**: Hard limit of `config.llm.maxSteps` iterations per call. If exceeded, the loop terminates and returns a partial result.

### [`llm/prompt.ts`](file:///Users/ichadhr/Develop/node/meridian/prompt.ts) (current root → target `llm/prompt.ts`)

Builds the system prompt injected at position `[0]` of every LLM call.

| Function | Purpose |
| :--- | :--- |
| `buildSystemPrompt(role, context)` | Constructs the full system prompt for a given role — includes agent identity, current date/time, active config snapshot, lessons, pool memory context, and role-specific instructions |

## `llm/tools/` — Tool System

The tool system is split into **co-located group files** — each file owns both the **schema** (what the LLM sees) and the **handler** (what actually runs) for a logical group of tools.

### Folder Layout

```
llm/tools/
  ├── index.ts          ← merges all schemas into tools[], routes executeTool()
  │
  ├── screening.ts      ← agent loop: discover_pools, get_top_candidates, get_pool_detail, search_pools
  ├── deployment.ts     ← agent loop: deploy_position, get_active_bin
  ├── management.ts     ← agent loop: close_position, claim_fees, get_my_positions, get_position_pnl, get_wallet_positions
  │
  └── cmd/              ← on-demand / user-triggered tools (GENERAL role)
      ├── wallet.ts         get_wallet_balance, swap_token
      ├── token.ts          get_token_info, get_token_holders, get_token_narrative
      ├── smart-wallets.ts  add/remove/list/check_smart_wallets
      ├── lessons.ts        add_lesson, pin/unpin_lesson, list_lessons, clear_lessons
      ├── strategy.ts       add/list/get/set_active/remove_strategy
      ├── memory.ts         get_pool_memory, add_pool_note, get_performance_history, get_recent_decisions, set_position_note
      └── blacklist.ts      add/remove/list_blacklist, block/unblock/list_blocked_deployers
```

### Why Two Levels?

- **Root-level group files** (`screening.ts`, `deployment.ts`, `management.ts`) are the **main agent loop tools**. The autonomous cron cycles — SCREENER and MANAGER — run exclusively through these. They are the core of what Meridian does.
- **`cmd/` sub-folder** contains **on-demand tools** used by the GENERAL role when a user sends a command (e.g. "show my blacklist", "add a lesson", "check wallet balance"). They support the main loop but are never called autonomously.

### How `index.ts` Works

`index.ts` is the only file imported by `agent.ts`. It:
1. Imports all group files (both root-level and `cmd/`)
2. Merges their `definitions` arrays into the single `tools` export the LLM receives
3. Routes `executeTool(name, args)` to the correct group handler by iterating the groups

```ts
// llm/tools/index.ts (simplified)

import * as screening  from "./screening.js";
import * as deployment from "./deployment.js";
import * as management from "./management.js";
import * as wallet     from "./cmd/wallet.js";
// ... all cmd/ imports

const groups = [screening, deployment, management, wallet, ...];

// LLM sees all schemas merged into one flat array
export const tools = groups.flatMap(g => g.definitions);

// executeTool routes to the right group handler
export async function executeTool(name: string, args: unknown) {
  for (const group of groups) {
    const result = await group.handle(name, args);
    if (result !== undefined) return result;
  }
  throw new Error(`Unknown tool: ${name}`);
}
```

### How Each Group File Works

Every group file exports two things — `definitions` and `handle`:

```ts
// llm/tools/cmd/lessons.ts (example)

export const definitions: ToolDefinition[] = [
  {
    type: "function",
    function: {
      name: "add_lesson",
      description: `...`,
      parameters: { type: "object", properties: { rule: { type: "string" } }, required: ["rule"] }
    }
  },
  // ... other lesson tool schemas
];

export async function handle(name: string, args: unknown): Promise<unknown> {
  switch (name) {
    case "add_lesson":    return await addLesson(args);
    case "list_lessons":  return await listLessons(args);
    case "pin_lesson":    return await pinLesson(args);
    case "unpin_lesson":  return await unpinLesson(args);
    case "clear_lessons": return await clearLessons(args);
    default: return undefined; // not handled by this group
  }
}
```

## How to Add a New Tool

> [!IMPORTANT]
> Adding a new tool is **always a single-file change**. Find the right group file, add the schema to `definitions[]` and the case to `handle()` in the same edit. No other files need to change.

### Step 1 — Pick the right group file

| Tool type | File to edit |
| :--- | :--- |
| New pool screening / discovery | `llm/tools/screening.ts` |
| New deployment variant | `llm/tools/deployment.ts` |
| New position lifecycle action | `llm/tools/management.ts` |
| New wallet / swap action | `llm/tools/cmd/wallet.ts` |
| New token research action | `llm/tools/cmd/token.ts` |
| New smart wallet action | `llm/tools/cmd/smart-wallets.ts` |
| New lesson / memory action | `llm/tools/cmd/lessons.ts` |
| New strategy action | `llm/tools/cmd/strategy.ts` |
| New pool memory / history | `llm/tools/cmd/memory.ts` |
| New blacklist / deployer action | `llm/tools/cmd/blacklist.ts` |
| Entirely new category | Create a new file, add it to `index.ts` groups array |

### Step 2 — Add schema + handler in the same file

```ts
// In definitions[]:
{
  type: "function",
  function: {
    name: "my_new_tool",
    description: `Clear description of when the LLM should call this.`,
    parameters: {
      type: "object",
      properties: {
        my_param: { type: "string", description: "..." }
      },
      required: ["my_param"]
    }
  }
},

// In handle() switch:
case "my_new_tool": {
  const { my_param } = args as { my_param: string };
  return await myActualImplementation(my_param);
}
```

### Step 3 — Register it in `agent.ts` role filters

Open `llm/agent.ts` and add the tool name to the relevant role sets:
- `SCREENER_TOOLS` — if the autonomous screener should be able to call it
- `MANAGER_TOOLS` — if the autonomous manager should be able to call it
- `GENERAL_INTENT_ONLY_TOOLS` + the right `INTENT_TOOLS` bucket — if it's a user command

> [!NOTE]
> If you skip Step 3, the tool exists but the LLM will never receive it in its filtered tool list for the relevant role — it will be invisible to the agent even though it's registered.

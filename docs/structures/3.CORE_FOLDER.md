# 3. Core Folder Specification

The `core/` directory contains the pure business logic, trading rules, and state management of the Meridian agent. It is designed to be **platform-independent and I/O-free**, importing only from `providers/` for network communications and `config/paths.ts` for file paths.

> [!IMPORTANT]
> **Folder Behavior & Philosophy:**
> 1. **The Gate File Rule**: `core/index.ts` is the **only file** imported from outside this folder. It is a barrel re-export of all public functions from every core sub-file. No individual core files (`core/lessons.ts`, `core/state.ts`, `core/pool-memory.ts`, etc.) should ever be imported directly by files outside `core/`. No files inside sub-folders (`core/live/`, `core/vp/`) should ever be imported from outside at all.
> 2. **Dispatcher Pattern**: `core/state.ts` is the **internal dispatcher** — it routes position operations to `core/live/` or `core/vp/` based on address prefix (`vp:xxx`) or `DRY_RUN` flag. Callers never import from sub-modules directly.
> 3. **Shared Routine & Logic Parity**: VP and Live positions share the **exact same execution routine** — same close rules, same PnL math, same SDK calls. The only difference is that VP does not submit an on-chain transaction. VP is **not a simulation with fake numbers** — it reads real bin state, real fee accumulators, and real price data from the chain via the Meteora SDK every cycle.

```
  Outside code (index.ts / llm/ / interfaces/ / providers/)
       │
       │  import { recordPerformance, getMyPositions, closePosition } from "core/index.ts"

  ┌─────────────────────────────────────────────┐

  (dispatcher)     lessons.ts    close-rules.ts  pnl.ts
        │          pool-memory.ts archive.ts     screen.ts

  ┌─────┴─────┐

            merge.ts
            digest.ts

  config/paths.ts ← all file path constants (imported by core/, llm/, cli.ts, index.ts)
```

## `core/state.ts` — The Internal Dispatcher

`core/state.ts` is the internal routing layer for positions. Called only from within `core/index.ts`, it dispatches without the caller knowing whether the target is live or virtual:

- **Live** → `core/live/state.ts` — signs and submits on-chain transactions via `providers/`
- **VP** → `core/vp/state.ts` — reads/writes to `vp_state.json`

Both paths then call the same shared engines:
- **`core/pnl.ts`** — Q64.64 SDK math, real bin share data, real fee accumulators
- **`core/close-rules.ts`** — stop-loss, take-profit, trailing TP, OOR, low-yield

```ts
/**

export function trackPosition(params: TrackPositionParams): string {
  if (process.env.DRY_RUN === "true") {
    return trackVpPosition(params);  // → core/vp/state.ts
  }
  return trackLivePosition(params);  // → core/live/state.ts

/**
 * Close a position. Routes based on address prefix.
 */
export async function closePosition(positionAddress: string, reason: string): Promise<any> {
  if (positionAddress.startsWith("vp:")) {
    const vpId = positionAddress.slice(3);
    return closeVpPosition(vpId, reason);    // → core/vp/manage.ts
  } else {
    return closeLivePosition({ position_address: positionAddress, reason });  // → core/live/state.ts
  }
}

 * Live: writes to live_state.json
 * VP:   writes to vp_state.json
 */
export function setPositionInstruction(positionId: string, instruction: string | null): boolean {
  if (positionId.startsWith("vp:")) {
    return setVpPositionInstruction(positionId, instruction);
  }
  return setLivePositionInstruction(positionId, instruction);
}
```

## VP vs Live — What's Different, What's the Same

| Step | Live | VP |
| :--- | :--- | :--- |
| Pool screening & scoring | ✅ Same | ✅ Same |
| Bin range calculation | ✅ Meteora SDK | ✅ Same SDK |
| **Deploy transaction** | ✅ **On-chain, real SOL** | ❌ **Skipped — state saved to `vp_state.json`** |
| Fetch live bin state per cycle | ✅ `getBinsInRange()` RPC | ✅ Same RPC call |
| PnL calculation | ✅ `core/pnl.ts` | ✅ Same function |
| Close rules evaluation | ✅ `core/close-rules.ts` | ✅ Same function |
| Gas estimation per cycle | ✅ Real RPC | ✅ Same RPC call |
| **Close transaction** | ✅ **On-chain** | ❌ **Skipped — state updated in JSON** |
| Pool memory recording | ✅ `core/pool-memory.ts` | ✅ Same (VP records too) |
| Position instructions | ✅ `core/state.ts` (dispatcher) | ✅ Same function |
| Briefing date tracking | ✅ `core/state.ts` (dispatcher) | ✅ Same function |

## Data Flow: Where State Lives

### Live Positions
```
  Deploy → live_state.json                        (open positions, live tracking)
  Close  → archives/live-archive-YYYY-MM.jsonl    (append-only JSONL)
         → lessons.json                           (auto: performance record + derived lesson)
         → pool-memory.json                       (auto: pool deploy history)
         → signal-weights.json                    (auto: Darwin recalc every 5 closes)
         → user-config.json                       (auto: threshold evolution every 5 closes)
         → HiveMind API                           (auto: pushes lesson + performance event)
```

### VP (Virtual Positions)
```
  Deploy → vp_state.json                          (open VPs, tracked locally)
  Close  → archives/vp-archive-YYYY-MM.jsonl      (append-only JSONL)
         → pool-memory.json                       (auto: VP also records pool deploy history)

  ⚠ VP does NOT automatically feed lessons.json, signal-weights.json,
    or threshold evolution. VP closes are archived but not curned (learned from).
```

> [!IMPORTANT]
> **Manual Curning for VP**: To feed VP closed positions into the learning pipeline
> (lessons, Darwin weights, threshold evolution), run the backfill script manually:
> ```
> node scripts/backfill-vp-archive.js
> ```
> This reads all `archives/vp-archive-*.jsonl`, deduplicates against `lessons.json`,
> calls `recordPerformance()` for each new record in chronological order, then restores
> `pool-memory.json` from the server canonical at `archives/pool-memory.json`.
> Hive pushes are disabled during backfill — no outbound events for historical closes.

### Why VP Learning is Manual

Live positions reflect real capital risk — their outcomes immediately feed the agent's next decision. VP positions are paper trades; their lessons should be reviewed and backfilled deliberately, not mixed automatically into the live learning stream. This also allows excluding invalid VP records (e.g. Meteora OHLCV validation failures) before they pollute the lesson corpus.

## Naming Convention — `{functionName}{Live|Vp}`

All position-specific functions must follow the pattern **`{functionName}{Live|Vp}`** — camelCase, variant name capitalized as suffix. This makes the dispatcher self-documenting: you can read which variant is live and which is VP just from the function names, without any comments.

```ts
// core/live/state.ts
export function trackLivePosition(params: TrackPositionParams): string { ... }
export function listLivePositions(openOnly?: boolean): TrackedPosition[] { ... }
export function getLivePosition(address: string): TrackedPosition | null { ... }
export function recordLiveClaim(address: string, feesUsd: number): void { ... }
export function recordLiveClose(address: string, reason: string): void { ... }

// core/vp/state.ts
export function trackVpPosition(params: TrackPositionParams): string { ... }
export function listVpPositions(statusFilter?: string): VpPosition[] { ... }
export function getVpPosition(id: string): VpPosition | null { ... }
export function recordVpClose(id: string, reason: string, pnl: PnL): boolean { ... }

// core/state.ts — dispatcher
export function trackPosition(params: TrackPositionParams): string {
  if (process.env.DRY_RUN === "true") return trackVpPosition(params);
  return trackLivePosition(params);
}
```

| Variant suffix | Variant | State file |
| :--- | :--- | :--- |
| `Live` | Live on-chain position | `live_state.json` |
| `Vp` | Virtual paper position | `vp_state.json` |

> [!IMPORTANT]
> Never export two functions with the same base name from the same file. If a module has two variants, name them distinctly: e.g. `trackLivePosition` vs `trackVpPosition`.
